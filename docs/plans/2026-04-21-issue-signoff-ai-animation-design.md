## Problem Statement

当前签发页右侧已经有 `签发 AI复核` 区块，也已经有问题文案、检查项和最终结论，但它是一次性静态出现的。

这会带来两个问题：

1. 用户看不到“系统正在怎么想”，红框区域像一块静态结果卡，不像一个正在工作的签发复核 Agent。
2. 签发阶段的复核维度虽然已经列出来了，但因为没有过程感，用户很难感知到它真的经历了：
   - 拿到问题
   - 进入思考
   - 复核原始数据
   - 检查样品数量
   - 检查设备适配性
   - 检查标准引用准确性
   - 最终形成签发建议和结论

这次要补的不是新业务节点，也不是再加更多规则。

就是把现有签发 AI 复核，做成一个有阶段、有节奏、有信任感的可视化过程。

## What Makes This Cool

最有意思的地方，不是“加动画”这三个字。

真正有价值的是，用户会从“这是一段静态文案”切换成“我能看到系统正在一步一步把签发判断做完”。

这会让签发页更像一个最终放行台，而不是一个把结果先写死在页面上的 demo 卡片。

如果做对了，红框区域会给人一种很明确的感觉：

- 系统先拿到了问题
- 然后进入思考
- 一项一项做关键检查
- 最后才给出建议和结论

这会直接提升签发动作的可信度。

## Constraints

- 这次只做演示版体验增强，不改签发业务边界
- 不改当前页面信息架构，仍然保持红框区域是 `签发 AI复核`
- 不引入新的后端协议，优先复用现有 `issue-review` API
- 动画必须服务信息表达，不做纯装饰 loading
- 风格必须沿用现有系统语言：
  - 浅底
  - 轻玻璃感
  - teal 主色
  - 圆角卡片
- 要与 `inspection-tasks` 原始数据录入页已经存在的 AI 复核动画语言保持同一家族感
- 检查顺序至少覆盖：
  - 收到问题 / Prompt
  - 思考模式
  - 复核原始数据
  - 检查样品数量
  - 检查设备适配性
  - 检查标准引用准确性
  - 最终建议
  - 最终结论

## Premises

1. 这次不需要做流式 SSE，前端阶段 reveal 就足够支撑演示版。
2. 现有 `src/lib/inspection-issue-review.ts` 已经有签发阶段 narrative 和 result 语义，应该作为动画编排的单一语义源。
3. 现有签发页 `src/app/issue-tasks/page.tsx` 已经具备问题文案、复核按钮和 trace 展示，适合在原位增强，不需要重做结构。
4. 最稳的方案是：点击 `AI复核` 后，同时触发：
   - 固定阶段动画
   - 现有 `issue-review` API 请求
5. 动画结束后，应无缝落到真实返回的 trace 和 summary，而不是保留两套内容并列。
6. “确认签发”按钮仍然只在签发 AI 复核通过后解锁，动画不能改变这个门槛。

## Approaches Considered

### Approach A: 轻量假 loading

点击 `AI复核` 后，只显示一个 spinner 或 shimmer，再在结束时一次性展示完整 trace。

- Effort: S
- Risk: Low
- Pros:
  - 改动最少
  - 实现最快
- Cons:
  - 用户仍然看不到“系统是怎么一步一步想的”
  - 和你要求的“模拟 LLM 拿到问题并开始思考”不匹配
  - 很容易显得廉价

### Approach B: 阶段式 reveal 动画

点击 `AI复核` 后，前端按固定 narrative 逐条 reveal：

- 收到问题
- 进入思考
- 原始数据复核
- 样品数量检查
- 设备适配性检查
- 标准引用检查
- 最终建议
- 最终结论

同时并行请求当前 `issue-review` API，动画结束后用真实返回结果替换或 hydrate。

- Effort: M
- Risk: Low
- Pros:
  - 最符合这次演示目标
  - 不改 API 协议
  - 可直接复用原始数据环节那套成熟思路
  - 结果和动画语义可以统一
- Cons:
  - 需要给签发阶段补一层前端状态机
  - 需要稍微扩充 `inspection-issue-review.ts` 的 narrative，使“思考模式”表达更强

### Approach C: 真流式签发 AI

后端改成流式事件推送，前端按服务端返回的 step 实时渲染。

- Effort: L
- Risk: Med
- Pros:
  - 长期最真实
  - 后面接真实 LLM 最顺
- Cons:
  - 对演示版是明显过度建设
  - 当前签发页没有必要为了这一段动画改成流式协议

## Recommended Approach

选择 **Approach B: 阶段式 reveal 动画**。

这是现在最对的做法。

### 设计原则

签发动画要和原始数据录入页的 AI 动画像一家人，但职责更像“最终放行检查”。

也就是说：

- 原始数据录入页更像“复原 + 复核”
- 签发页更像“最终把关 + 放行建议”

所以签发动画需要更强调：

- 判断链
- 风险点
- 最终建议

而不是只强调“系统在运行中”。

### 建议的阶段顺序

建议把现有签发 narrative 收敛成下面这条链：

1. **Prompt**
   - 收到签发问题
   - 明确当前任务、样品数量、设备和标准

2. **Think**
   - 进入思考模式
   - 把签发判断拆成四个检查维度

3. **Check**
   - 复核原始数据与公式

4. **Check**
   - 样品数量是否满足规范要求

5. **Check**
   - 当前设备是否适用于该检测项目

6. **Check**
   - 当前引用标准是否准确

7. **AI Suggestion**
   - 形成最终签发建议

8. **AI Conclusion**
   - 给出最终结论，是否可以进入签发

这里有一个关键判断：

“思考模式”不应该只是一个按钮 loading 状态。

它应该是一条真正的阶段节点，让用户在视觉上感知到系统先做了“拆问题”，再做逐项检查。

### 页面表现

红框区域建议保持现有结构，但增强为：

- 顶部：问题文案 + `思考中 / 已完成` 状态胶囊
- 中间：阶段进度条
- 下方：trace 条目逐条出现
- 最底部：最终建议 / 最终结论

其中每条 trace 不要同时出现。

要用 staged reveal：

- 新条目从下方轻微上浮进入
- 当前活跃条目有更明显的高亮和边框
- 状态胶囊和进度条同步推进

### 技术形状

建议直接复用现有原始数据页那套做法：

- 在 `src/app/issue-tasks/page.tsx` 内增加：
  - `issueReviewNarrative`
  - `visibleIssueReviewSteps`
  - `activeIssueReviewStepId`
  - 动画 timer 管理
- 点击 `AI复核` 时：
  - 并行启动 `runInspectionIssueReview(task.id)`
  - 并行启动 `runIssueReviewNarrative(task)`
- 动画完成后：
  - 用真实 API 返回的 trace / summary hydrate 当前叙事
  - 保持“确认签发”按钮只在 `passed === true` 时可用

### 语义源统一

不要再在页面里写一套新的静态步骤。

应该把签发阶段动画和最终结果都统一到：

- `src/lib/inspection-issue-review.ts`

这意味着这个文件需要承担：

- 问题生成
- 阶段 narrative
- 最终结果

如果当前 narrative 里还没有单独的 `Think` 和 `AI Suggestion` 阶段，就补进去。

## Open Questions

1. 最终建议和最终结论是否分成两条独立 trace，还是保留“最后一条 trace + summary”双层表达。  
我的建议是分开。用户更容易看懂“建议”与“结论”的差异。

2. 动画总时长要不要和原始数据页完全一致。  
我的建议是不用。签发页可以略短一点，但至少要有 4 秒左右过程感。

3. 是否要保留签发页当前顶部绿色成功 feedback。  
我的建议是保留，但不要抢过红框区域的主戏。

## Success Criteria

- 点击签发页 `AI复核` 后，红框区域不再一次性静态渲染所有 trace
- 用户能明显看到：
  - 收到问题
  - 进入思考
  - 四个检查项逐条推进
  - 最终建议
  - 最终结论
- 动画风格与原始数据录入页 AI 动画保持同一家族感
- 页面仍然沿用现有签发工作台视觉语言，不出现突兀的新风格
- 动画结束后，内容能够无缝落到真实 API 返回结果
- `确认签发` 的解锁逻辑保持不变

## Distribution Plan

这是现有 Web 应用中的签发工作台体验增强，不是独立交付物。

- 交付方式：随 `/issue-tasks` 页面一起发布
- 构建发布：沿用当前 Next.js 应用的现有发布路径
- 演示路径：
  1. 进入待签发任务
  2. 点击 `AI复核`
  3. 展示签发 LLM 思考链
  4. 看到最终建议和结论
  5. 解锁 `确认签发`

## Next Steps

1. 扩充 `src/lib/inspection-issue-review.ts`，补 `Think` 和 `AI Suggestion` 等阶段语义
2. 在 `src/app/issue-tasks/page.tsx` 中增加签发阶段动画状态机
3. 在 `src/app/issue-tasks/issue-tasks.css` 中补状态胶囊、进度条、活跃 trace 动效
4. 新增针对签发 narrative 的纯测试，锁定阶段顺序和关键文案
5. 以 `node --test` + `npm run build` 做最小验证

## What I noticed about how you think

- 你没有只说“这里加个动画”，你说的是“模拟 LLM 拿到用户问题然后开启思考模式”，说明你在意的是 Agent 的工作感，不是装饰效果。
- 你把签发阶段要检查的内容点得很具体，`样品数量、设备适配性、标准引用准确性`，这说明你关心的是“最终放行是否可信”。
- 你直接盯着红框这一个区域提需求，没有要求重做整页，这种聚焦是好的。说明你知道这次要增强的是哪一段体验，而不是把页面一起推倒。
