## Problem Statement

当前检测链路已经能走到：

- 原始数据录入
- AI 复核
- 提交审核
- 审核通过进入 `awaiting_issue`

但流程在两个地方断了。

第一，审核通过后，用户还停在审核页。系统虽然把任务推进到了待签发，但首页没有明确回流提醒，用户不知道下一步该去签发模块。

第二，签发模块还只是占位，没有真正的“最终放行台”。这意味着演示时流程看起来像是已经完整，实际上最后一步没有承接页面，也没有更严格的签发校验。

这次不是做长期架构，也不是上完整 LIMS。目标很窄，很实用：

1. 审核完成后回首页
2. 首页检测模块上出现“签发”角标
3. 用户点进签发模块后，看到一个像审核工作台但职责更明确的签发工作台
4. 在签发页里完成全量数据复核和最终签发

## What Makes This Cool

最有演示价值的点，不是“又多了一个页面”，而是整条检测链终于有了收口动作。

用户在演示里会清楚看到：

- 审核通过，不是状态默默变化，而是系统把任务送回首页提醒
- 首页不是死导航，而是会告诉用户“现在有待签发任务”
- 签发页不是再做一遍审核，而是把任务单详情、原始数据、已有 AI 结论和更严格的签发维度放在一个放行台里

这会让整条链从“能跑几步”变成“真的闭环”。

## Constraints

- 这次只做能跑通验收的演示版流程，不做正式签发系统
- UI 必须沿用现有 `review-tasks` / `inspection-workbench` 的工作台语言，不引入新设计系统
- 审核通过后必须回首页，而且是带一次性信号回首页，不是停在审核页提示用户自己返回
- 首页需要新增签发角标能力，至少体现在：
  - 检测大卡片
  - 展开后的 `签发` 模块卡片
- 签发页必须独立，不和审核页混在一个页面里
- 签发页右侧优先展示全量信息，不以备注框为中心
- 签发页的 AI 复核样式沿用现有“阶段过程 + 最终结论”的表达方式
- 新增的签发 AI 维度至少包含：
  - 样品数量是否符合规范
  - 使用设备是否合适
  - 引用标准是否准确
  - 原始数据与标准公式是否一致
- 当前仍然可以使用 mock 规则和 mock 结论，但文案和状态流必须像真系统

## Premises

1. 审核通过后，页面跳回首页 `/`，并带一个一次性信号，例如 `inspectionSignal=issue`。
2. 首页收到 `inspectionSignal=issue` 后，会自动展开 `检测` 模块一次，然后清掉这个信号。
3. 首页任务提醒逻辑要把 `awaiting_issue` 纳入可见状态。
4. 首页除了已有的“我的任务”“审核”角标外，要新增“签发”角标。
5. 点击首页检测模块中的 `签发` 卡片，进入新的独立页面，建议路由为 `/issue-tasks`。
6. 新签发页继续使用双栏工作台，左侧是待签发队列，右侧是当前任务的全量信息和最终签发动作。
7. 为了让签发动作真正闭环，任务状态需要新增最终态，建议使用 `issued`，表示已签发，不再停留在 `awaiting_issue`。
8. 点击“确认签发”后，任务进入 `issued`，从签发队列和首页签发角标里消失。

## Approaches Considered

### Approach A: 审核页扩展成审核+签发双模式

保留现有 `/review-tasks`，通过 tab 或 mode switch 同时承载审核和签发。

- Effort: M
- Risk: Med
- Pros:
  - 页面最少
  - 实现路径短
  - 不需要新增新路由
- Cons:
  - 审核和签发职责混在一起
  - 演示时不容易讲清“审核通过后回首页再进签发”
  - 后续一旦加更多签发规则，页面会迅速发胖

### Approach B: 独立签发工作台

审核页保持“人工审核”职责。审核通过后跳回首页，并通过首页角标把用户导向新的签发页。签发页独立承载最终放行。

- Effort: M
- Risk: Low
- Pros:
  - 业务语义最清楚
  - 最符合演示目标，用户能看到完整回流链
  - 签发页可以自然承载更多校验维度
  - 审核页和签发页样式相似，但职责不同，讲解最顺
- Cons:
  - 要新增一套路由、页面和首页角标
  - 需要补一个最终签发态

### Approach C: 首页右侧弹层式签发

审核通过后回首页，点击签发卡片只打开一个右侧抽屉，不做独立页面。

- Effort: S
- Risk: Med
- Pros:
  - 改动文件最少
  - 首页演示上手快
- Cons:
  - 首页会被过载
  - 全量数据不适合挤进首页弹层
  - 不像正式的业务节点，更像临时拼装

## Recommended Approach

选择 **Approach B: 独立签发工作台**。

这条路最适合你现在的目标。不是最小文件数，而是最清楚的演示闭环。

### 核心状态流

推荐状态流变成：

- `pending_claim`
- `in_experiment`
- `awaiting_raw_data`
- `awaiting_review`
- `awaiting_issue`
- `issued`

其中：

- 审核通过，`awaiting_review -> awaiting_issue`
- 确认签发，`awaiting_issue -> issued`

### 首页回流提醒

审核页点击“通过”后：

1. API 仍然把任务推进到 `awaiting_issue`
2. 前端不留在审核页，而是跳回 `/?inspectionSignal=issue`
3. 首页收到该信号后：
   - 自动展开 `检测` 模块一次
   - 清掉 URL 信号
4. 检测模块显示：
   - 大卡片总角标仍然表示检测链存在待处理任务
   - `签发` 模块卡片显示 `N · 待签发`

这里要补的不是 toast，而是明确的“下一站入口被激活”。

### 签发页信息架构

建议新增页面 `/issue-tasks`。

页面结构直接沿用审核页双栏语法：

- 顶部：`首页 / 检测 / 签发`
- 左栏：待签发队列
- 右栏：当前任务全量信息与签发动作

#### 左栏

左栏只做两件事：

- 快速定位待签发任务
- 展示最小必要摘要

每张卡片显示：

- 任务单号
- 样品名称
- 样品数量
- 检测项目
- 当前设备
- `待签发` badge

#### 右栏

右栏不再以备注框为中心，而是变成一个真正的最终放行台。建议按这个顺序：

1. **任务单数据详情**
   - 任务单号
   - 样品名称
   - 样品数量
   - 检测项目
   - 引用标准
   - 使用设备
   - 实验人员

2. **原始数据还原**
   - 直接复用当前原始数据录入页的表格样式
   - 不可编辑，只读展示

3. **签发 AI 复核**
   - 样式沿用现有 trace / summary 区域
   - 但维度扩成四条以上

建议的签发 AI 复核维度：

- `Check 1` 原始数据与标准公式是否一致
- `Check 2` 样品数量是否满足该标准最小组数要求
- `Check 3` 当前设备是否适用于该检测项目
- `Check 4` 引用标准编号和检测项目是否匹配
- `AI` 最终签发建议

4. **操作区**
   - `重新复核`
   - `确认签发`

## Open Questions

1. 首页检测大卡片总角标在存在 `awaiting_issue` 时，是继续显示统一的“待处理”，还是直接跟随最新任务状态显示“待签发”。
2. 签发完成后，是否需要留下“签发成功，已归档”的一次性首页反馈，还是直接让角标消失即可。
3. 当前签发页是否需要备注框。如果只是演示版，可以先不要，保持页面重心在“全量信息 + AI 复核 + 确认签发”。

## Success Criteria

- 审核页通过后，页面自动跳回首页
- 首页检测模块自动展开一次
- 首页 `签发` 模块出现角标，能明确提示存在待签发任务
- 用户点击 `签发` 能进入独立签发工作台
- 签发页左侧能选择待签发任务
- 签发页右侧能看到任务单详情和原始数据
- 签发 AI 复核能展示 4 条以上维度检查
- 点击“确认签发”后，任务从待签发队列中消失

## Distribution Plan

这是现有 Web 应用中的新增业务流，不是独立交付物。

- 交付方式：随 Next.js Web 应用一起发布
- 构建发布：继续沿用当前仓库已有构建流程
- 演示路径：
  1. 原始数据录入并提交审核
  2. 审核通过
  3. 回首页看到签发角标
  4. 点进签发页完成 AI 复核和确认签发

## Next Steps

2. 审核页“通过”改成跳首页，并增加 `inspectionSignal=issue`
3. 首页检测模块新增 `inspectionIssueBadge`

## What I noticed about how you think

- 你没有说“把签发模块补一下”，你说的是“审核完成后需要跳转到首页，此时签发模块卡片上需要有角标提示”。你盯的是流程回流，不只是页面按钮。
- 你没有满足于“签发页也做一个通过按钮”，你明确要求“右侧只展示所有的数据，包括任务单数据详情和原始数据”，说明你在意的是签发动作的信任感。
- 你对 AI 复核维度给得很具体，不是笼统的“加强校验”，而是点名了“样品数量、设备适配、标准准确性”。这让设计边界很清楚。
