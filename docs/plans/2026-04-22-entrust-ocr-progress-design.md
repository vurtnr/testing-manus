## Problem Statement

当前 [委托受理页](/Users/jiaoyumin/workspace/testing-manus/src/app/entrust/page.tsx) 的核心动作链已经存在：

1. 上传纸质委托单照片
2. 点击 `开始 OCR 识别`
3. 等接口返回
4. 右侧显示 OCR 摘要
5. 点击 `确认按照片原件入库`

但现在这条链路在用户感知上有两个明显缺口：

1. 点击 `开始 OCR 识别` 后，右侧大面积空白，没有过程感。用户不知道系统是在纯 OCR、在调 LLM，还是卡住了。
2. `确认按照片原件入库` 虽然逻辑上已经受 `!ocrResult` 控制，但界面没有把“当前不可点击”这件事表达得足够明确，尤其在原型演示里，这会让人误判流程边界。

你这次要补的不是识别能力本身，而是识别过程的可见性：

- 在右侧增加一个动画效果的进度条
- 明确告诉用户系统正在使用 LLM 进行 OCR 识别与分析
- 在识别完成前，`确认按照片原件入库` 保持无法点击

这是把“黑箱等待”变成“有解释的等待”。

## Demand Evidence

这不是泛泛的“优化体验”。

你的描述里有两个很清楚的 pull：

- `需要在右侧增加一个动画效果的进度条告知用户当前正在使用LLM进行OCR识别并进行分析`
- `确认按照片原件入库按钮应该处在无法点击的状态`

说明当前演示已经不是缺功能，而是缺“流程可信度”。内部演示里，用户会立刻问：

“我点了之后系统到底在干什么？”

以及：

“现在是不是已经可以入库了？”

## Status Quo

当前实现有这些事实：

- [page.tsx](/Users/jiaoyumin/workspace/testing-manus/src/app/entrust/page.tsx#L63) 中 `handleRecognize()` 只有一个 `recognizing` 布尔状态。
- OCR 请求走 [runEntrustOcr()](/Users/jiaoyumin/workspace/testing-manus/src/lib/api.ts) -> [POST /api/entrust/ocr](/Users/jiaoyumin/workspace/testing-manus/src/app/api/entrust/ocr/route.ts#L1)。
- 右侧在 `!ocrResult` 时只显示一段静态提示文案，没有“处理中”的专属视觉状态。
- `确认按照片原件入库` 按钮在逻辑上已经 `disabled={!selectedImage || !ocrResult || submitting}`，但 [entrust.css](/Users/jiaoyumin/workspace/testing-manus/src/app/entrust/entrust.css#L1) 里没有专门的 `:disabled` 样式，所以“禁用态”视觉不够强。

所以当前问题不在后端，也不在状态机本身，而在用户看不见状态机。

## Target User & Narrowest Wedge

目标用户是前台受理或内部门户演示中的操作人。

他们最小的真实需求不是“看到完整 OCR 中间结果”，而是：

- 我点完 `开始 OCR 识别`
- 系统马上告诉我它正在工作
- 我能知道现在还不能入库
- OCR 完成后，右侧自然切到摘要结果

最小楔子就是：

> 在右侧 OCR 摘要区加入一个客户端驱动的 LLM OCR 过程展示，并把入库按钮的禁用态做成明确的视觉锁定。

## Constraints

- 当前还是内部项目的演示/原型阶段，不要求真实流式 OCR 事件回传。
- 不改 OCR API 协议，不强制后端做 SSE。
- 动画必须落在右侧摘要区，不能打断左侧上传区主流程。
- 入库按钮仍然位于右侧底部 sticky bar，不改信息架构。
- 禁用态必须同时满足：
  - 逻辑不可点击
  - 视觉上明显不可操作

## Premises

1. 这个问题的核心不是“速度慢”，而是“等待时没有解释”。
2. 在演示版里，前端编排一个与 OCR 语义一致的 staged progress，比改流式后端更稳。
3. 当前 `recognizing` 已经足够作为单一信号驱动进度动画，不需要额外状态源。
4. `确认按照片原件入库` 的禁用态不能只靠 DOM `disabled` 属性，必须在样式和文案上一起表达。

## Approaches Considered

### Approach A: 右侧只加 spinner 和一句“识别中”

点击 OCR 后，右侧替换成一个圆形 loading 和一句状态文案，识别结束再回到结果摘要。

- Effort: S
- Risk: Low
- Pros:
  - 最快
  - 基本不需要新结构
- Cons:
  - 太像普通接口等待
  - 不符合“正在使用 LLM 进行 OCR 识别并分析”的要求
  - 演示感弱，看起来像卡住

### Approach B: 右侧 staged progress，模拟 OCR + LLM 分析过程

点击 OCR 后，右侧显示一个进度条和分阶段 trace，例如：

- 读取照片
- OCR 提取文字
- LLM 识别字段关系
- 结构化摘要生成
- 等待用户确认入库

识别完成后自动切回摘要结果。

- Effort: M
- Risk: Low
- Pros:
  - 最符合你的需求
  - 用户能理解系统在做什么
  - 和现有 `inspection-tasks` / `issue-tasks` 的 AI 过程展示是一家人
- Cons:
  - 需要补一套前端叙事步骤和样式
  - 比简单 spinner 稍重

### Approach C: 真流式 OCR 事件回传

后端把 OCR 和字段分析拆成阶段事件，前端按服务端事件驱动右侧进度条和 trace。

- Effort: L
- Risk: Medium
- Pros:
  - 最真实
  - 前后端语义完全一致
- Cons:
  - 对当前原型阶段太重
  - 需要改 API 协议和错误处理
  - 会让本轮需求从体验增强变成系统重构

## Recommended Approach

选择 **Approach B**。

这是当前原型阶段最对的取舍。

原因很简单：

- 你要的是“让用户知道系统在用 LLM 做 OCR 识别与分析”
- 不是“把后端 OCR 协议全部流式化”

Approach B 能用现有 `recognizing` 状态把这件事讲清楚，而且能直接复用当前项目已经成熟的“AI 过程感”语言。

## Open Questions

1. OCR 过程中是否需要显示具体百分比。  
   建议显示伪进度条，但不承诺精确百分比，用阶段 reveal 更稳。

2. 识别失败后右侧是否保留失败 trace。  
   建议保留“进行到哪一步失败”的状态块，再附错误文案，比直接回到空白区更可信。

3. 入库按钮在禁用时是否需要改文案。  
   建议保持按钮文案不变，但在按钮上方补一行灰色说明：
   `请先完成 OCR 识别后再按照片原件入库`

## Success Criteria

1. 点击 `开始 OCR 识别` 后，右侧不再是空白，而是立即进入带动画的进度展示。
2. 右侧进度展示明确传达“系统正在使用 LLM 做 OCR 识别与分析”。
3. OCR 识别完成前，`确认按照片原件入库` 在逻辑和视觉上都不可点击。
4. OCR 成功后，右侧自然切换到结构化摘要结果。
5. OCR 失败时，右侧保留明确错误态，而不是回到无状态空白。
