## Problem Statement

当前 [审核工作台](/Users/jiaoyumin/workspace/testing-manus/src/app/review-tasks/page.tsx) 的左侧已经能列出 `awaiting_review` 任务，但右侧还停留在最早期版本，只包含：

- 审核意见备注框
- `通过`
- `退回`

这导致审核人在当前页做判断时缺少上下文。你截图里暴露的问题很直接：

1. 右侧没有任务单数据详情，审核人看不到合同编号、样品数量、检测项目、引用标准、设备等关键信息。
2. 右侧没有原始数据还原表格，审核人无法直接核对“提交上来的数据”到底是什么。
3. 现有页只展示左侧卡片上的一句 `AI结论`，这更像提醒，不像真正的审单台。

而同一条链路里，[签发页](/Users/jiaoyumin/workspace/testing-manus/src/app/issue-tasks/page.tsx) 已经有更完整的右侧信息架构：

- 任务单数据详情
- 原始数据还原
- 已有 AI 结论
- 操作区

所以这次需求不是要发明新流程，而是把审核页补齐到一个真正可审的状态。

## What Makes This Cool

最值钱的点不是“多展示几个字段”，而是把审核页从一个按钮页变成一个判断页。

审核人应该在同一个视图里完成三件事：

1. 看任务单元数据
2. 看原始数据表格
3. 对照 AI 结论做人工判断

这样“通过”才像一个被信息支撑的动作，不像盲点按钮。

## Constraints

- 保留当前 `/review-tasks` 路由，不新增审核详情页。
- 保留现有左队列 + 右工作区的工作台骨架。
- 尽量复用现有 [getInspectionTaskDetail()](/Users/jiaoyumin/workspace/testing-manus/src/lib/api.ts#L471) 返回的数据，不新增后端接口。
- 视觉语言必须沿用当前 `review-tasks` / `issue-tasks` / `inspection-workbench` 的工作台风格，不引入新设计系统。
- 审核页展示的原始数据必须是只读，不允许在这里修改。录入和改单动作仍然发生在实验任务工作台。

## Premises

1. 审核人做“通过 / 退回”之前，必须同时看到任务单详情和原始数据，不然审核动作缺乏依据。
2. 当前 API 已经足够。`InspectionTaskDetail` 本身就包含任务单字段、`rawDataPreview`、`aiReviewSummary` 和审核备注字段，所以这次问题主要是前端信息架构，不是后端数据能力。
3. 审核页和签发页不应该各自长出一套不同的详情区，不然后面同一批字段会重复维护两遍。
4. 审核页里的原始数据应当只读展示，职责是核对，不是重新录入。

## Approaches Considered

### Approach A: 在现有审核页右侧直接补三段详情

保留当前页面结构，用户点击左侧任务后，右侧按顺序展示：

1. 任务单数据详情
2. 原始数据还原表格
3. 已有 AI 结论
4. 审核意见与操作区

Effort: S
Risk: Low

Pros:
- 改动范围最小，完全符合“在现有界面上增加展示”的要求。
- 后端基本不用动，主要是页面补 detail loading 和展示区块。
- 最快能把审核页补到可用状态。

Cons:
- 如果直接在 `review-tasks/page.tsx` 里手写一套详情布局，和 `issue-tasks` 会逐渐分叉。
- 后续签发页如果继续改字段顺序或展示样式，审核页容易跟丢。

Reuses:
- [getInspectionTaskDetail()](/Users/jiaoyumin/workspace/testing-manus/src/lib/api.ts#L471)
- [InspectionTaskDetail](/Users/jiaoyumin/workspace/testing-manus/src/lib/api.ts#L163)
- [issue-tasks 页面现有右侧区块](/Users/jiaoyumin/workspace/testing-manus/src/app/issue-tasks/page.tsx#L320)

### Approach B: 抽共享只读详情区，审核页和签发页共用

把 `issue-tasks` 里现有的“任务单详情 + 原始数据表格 + AI结论摘要”抽成共享展示组件，审核页和签发页都使用同一套只读区块。审核页在共享区块下方保留备注框和 `通过 / 退回`。

Effort: M
Risk: Medium

Pros:
- 两个工作台对同一份数据使用同一种展示语言，长期最稳。
- 后续增加字段时只改一处。
- 审核页和签发页的关系会更清楚：同一份详情，不同动作层。

Cons:
- 比直接补页面多一步抽象设计。
- 如果这次只是为了快速补展示，会感觉略重。

Reuses:
- [issue-tasks 详情区的现有字段编排](/Users/jiaoyumin/workspace/testing-manus/src/app/issue-tasks/page.tsx#L341)
- [review-tasks 的队列/动作骨架](/Users/jiaoyumin/workspace/testing-manus/src/app/review-tasks/page.tsx#L81)

### Approach C: 审核页右侧做 tab 切换区

右侧不是顺序堆叠，而是做 3 个 tab：

- 任务单数据
- 原始数据
- AI结论 / 审核动作

Effort: M
Risk: Medium

Pros:
- 当字段很多时，右侧不会过长。
- 更适合未来加入原始图片缩略图、AI 标红说明等扩展区。

Cons:
- 审核动作前还要点 tab，看信息的成本更高。
- 对这次需求来说有点过设计，违背“在现有界面补详情”的直觉。

Reuses:
- 现有 `review-tasks` 右侧操作区
- 现有工作台的 badge / section / card 视觉语言

## Recommended Approach

选择 **Approach B**。

原因很简单。用户要的是“在审核状态的任务单现有的界面上增加详细的任务单数据与原始数据的展示”，不是临时 patch 一个更长的右栏。现在 [签发页](/Users/jiaoyumin/workspace/testing-manus/src/app/issue-tasks/page.tsx#L320) 已经有了一套成熟的只读详情结构，这就是现成答案。

如果审核页自己再写一套，今天能交差，明天就开始漂。

Approach B 的本质是：

- 审核页和签发页共享“看什么”
- 审核页保留“怎么判”
- 签发页保留“怎么放行”

这是更完整也更干净的做法。不是大重构，还是一口能吃下的湖。

## Open Questions

1. 审核页是否需要同时展示原始记录图片文件名，甚至图片缩略图。  
   当前签发页只显示文件名。建议审核页先跟签发页一致，只显示文件名，不先上缩略图。
2. 审核页是否需要高亮 AI 曾标红的问题单元格。  
   如果当前 `rawDataPreview.issueCell` 已经存在，建议只读表格里同步标色，这样审核人能直接看到人工改过的位置。
3. 审核意见区域要不要继续放在最上面。  
   建议下移到详情展示之后，保持“先看数据，再做判断”的顺序。

## Success Criteria

1. 在 `/review-tasks` 选择一条待审核任务后，右侧能加载并展示完整的任务单数据详情。
2. 右侧能展示原始数据还原表格，而不是只有一句 “已上传原始记录图片”。
3. 右侧能展示已有 AI 结论，和任务单详情、原始数据并列成为审核依据。
4. 审核意见备注框与 `通过 / 退回` 仍然保留，但不再是右栏唯一内容。
5. 若任务缺少原始数据预览，右侧有明确空态提示，而不是整页空白。
6. 审核页与签发页的数据展示风格保持同一家族，不出现两套字段顺序和样式定义。

## Distribution Plan

这是现有 Web 工作台上的信息架构增强，沿用当前 Next.js 应用的既有发布链路即可，不需要新增交付物或新的部署通道。
